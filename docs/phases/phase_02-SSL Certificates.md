## Objective

Generate locally-trusted HTTPS certificates for all development hostnames and place them in `~/Projects01/docker-env/ssl_files/`, ready to be mounted by Nginx (Phase 3) and Apache (Phase 4).

This phase is **host-only**. No Docker involved.

## Certificates Produced

| File | SAN entries | Purpose |
|---|---|---|
| `wildcard.test.crt` + `wildcard.test.key` | `DNS:*.test`, `DNS:test` | Covers `site1.test`, `site2.test`, `dev.test`, and any future `*.test` hostname |
| `localhost.crt` + `localhost.key` | `DNS:localhost`, `IP:127.0.0.1`, `IP:::1` | Covers `localhost`, `127.0.0.1`, and `::1` |

**Location:** `~/Projects01/docker-env/ssl_files/`

**Why two certs instead of one:**
- A `*.local` wildcard does not cover `localhost` or `127.0.0.1` — these are not subdomains of `.local`.
- Browsers treat `localhost` specially; a matching cert avoids warnings on `https://localhost`.
- mkcert makes both with minimal extra effort.

**Expiry:** Both certificates expire on **11 January 2029**.

### Step 2.3 — Generate the wildcard `*.local` certificate

**Commands run:**

```bash
cd ~/Projects01/docker-env/ssl_files
mkcert -cert-file wildcard.test.crt -key-file wildcard.test.key "*.test" "test"
```

**Output:**

```
Created a new certificate valid for the following names 📜
 - "*.local"
   Warning: many browsers don't support second-level wildcards like "*.local" ⚠️
 - "local"

Reminder: X.509 wildcards only go one level deep, so this won't match a.b.local ℹ️

The certificate is at "wildcard.test.crt" and the key at "wildcard.test.key" ✅

It will expire on 11 January 2029 🗓
```

**Result:** ✅ Pass

**Interpretation of warnings:**
- `Warning: many browsers don't support second-level wildcards like "*.local"` — a wildcard `*.local` matches exactly one level: `site1.test`, `site2.test`, `dev.test` ✅. It does not match `a.b.test`. All planned hostnames are one level under `.test`, so this is fine.
- `X.509 wildcards only go one level deep` — same point, no action needed.
- Both `*.test` and bare `test` are included as SAN entries; the bare form is included because some clients expect the wildcard's base domain to also be listed.

### Step 2.4 — Generate the `localhost` certificate

**Command run (as executed):**

```bash
cd ~/Projects01/docker-env/ssl_files & mkcert -cert-file localhost.crt -key-file localhost.key "localhost" "127.0.0.1" "::1"
```

**Output:**

```
[1] 2513
[1]  + done       cd ~/Projects01/docker-env/ssl_files

Created a new certificate valid for the following names 📜
 - "localhost"
 - "127.0.0.1"
 - "::1"

The certificate is at "localhost.crt" and the key at "localhost.key" ✅

It will expire on 11 January 2029 🗓
```

**Result:** ✅ Pass

**⚠️ Lesson learned — `&` vs `&&` in shell commands:**

The command used `&` (single ampersand) instead of `&&` (double ampersand) to chain the two commands:

```bash
cd ~/Projects01/docker-env/ssl_files & mkcert -cert-file ...
```

**What this means:**

| Operator | Behaviour |
|---|---|
| `&&` | Runs the second command **only if** the first succeeds. Sequential, dependent. |
| `&`  | Runs the **first** command in the **background**, then immediately runs the second — regardless of success. |

**Why it didn't cause a problem here:**
- The shell's working directory was already `ssl_files/` from the previous step, so the bare filenames `localhost.crt` and `localhost.key` landed in the correct place.
- The `[1] 2513` and `[1] + done` lines were the shell reporting the backgrounded `cd` as a job.

**Why this matters going forward:**
- `&` can silently produce wrong results if the shell's working directory or environment hasn't been set up before the next command runs.
- Always use `&&` when the second command depends on the first.
- **Correct form for this command:**

  ```bash
  cd ~/Projects01/docker-env/ssl_files && mkcert -cert-file localhost.crt -key-file localhost.key "localhost" "127.0.0.1" "::1"
  ```

- **Alternative, even safer** (no `cd` needed — use absolute paths in mkcert flags):

  ```bash
  mkcert -cert-file ~/Projects01/docker-env/ssl_files/localhost.crt \
         -key-file  ~/Projects01/docker-env/ssl_files/localhost.key \
         "localhost" "127.0.0.1" "::1"
  ```

**Note for future phases:** Prefer `&&` for chaining, and absolute paths wherever practical. Never `&` unless intentionally backgrounding a process.

## Rollback Procedure

If you need to undo Phase 2:

**Option A — Remove just the generated certificates:**

```bash
rm -rf ~/Projects01/docker-env/ssl_files
```

**Option B — Also uninstall the mkcert CA from your trust stores:**

```bash
mkcert -uninstall
```

This removes the mkcert CA from macOS and Firefox trust stores. You'd then need to re-run `mkcert -install` in the future to regenerate certificates.

**Option C — Full cleanup:**

```bash
mkcert -uninstall
rm -rf ~/Projects01/docker-env/ssl_files
```

No Docker state to clean up — nothing was created in this phase.
